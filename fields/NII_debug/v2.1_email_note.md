# v2.1 container — note for NII (email-ready)

## One-liner
v2.1 fixes the `PermissionError: nvcc` crash by bundling its own `nvcc` — the container is now fully
self-contained for the CUDA toolchain and depends on nothing from the host except the GPU driver.
Nothing changes on your side.

## What v2.1 fixes / guards against
The previous run crashed before training started with `PermissionError: nvcc`. Root cause: our
container shipped **no CUDA compiler (`nvcc`) of its own**, so during `torch.compile` it fell back to
the **host's** `nvcc` — which on the compute node is **non-executable** (a `noexec`-mounted/restricted
path, i.e. normal cluster security). PyTorch tolerates a *missing* nvcc but not a *non-executable*
one, so every rank failed at the first compile.

**v2.1** bundles its own `nvcc` and puts it first on `PATH`, so the container is fully self-contained
for the CUDA toolchain and never resolves (or depends on) anything from the host except the GPU
driver (via `--nv`). It is therefore unaffected by the host's `nvcc`, mount options, or `PATH` —
**nothing needs to change on your side.** We verified it end-to-end: it now clears the compile and
trains (including with a deliberately non-executable host `nvcc` bound in, reproducing the exact
failure condition).

## Broader hardening (not just nvcc)
While fixing this we audited the whole build/compile toolchain and made the container resolve
**all** of it from inside the image, so no host binary or library can shadow ours regardless of the
node's mounts, `PATH`, or security policy:

- **`nvcc`** — we ship our own (CUDA 13.0.88), first on `PATH`.
- **C/C++ compiler (`gcc`/`g++`)** — used by `torch.compile`/inductor to build its kernel wrappers;
  pinned to the in-image `/usr/bin/gcc-11` / `g++-11` (via `$CC`/`$CXX`), so a host-provided compiler
  can never be picked up.
- **`ptxas`, `cicc`, `nvlink`** (PTX→cubin) — bundled inside Triton/PyTorch and invoked by absolute
  path, never via `PATH`/host.
- **`as`, `ld`, binutils** — resolved from the in-image `/usr/bin`; we reordered `PATH` so the
  populated in-image directories are always searched **before** any empty, host-fillable ones.
- **CUDA runtime libraries** (`cudart`, `cudnn`, `cublas`, `nccl`, `nvrtc`, `nvshmem`, …) — all
  bundled as pip wheels and resolved via the libraries' own `RPATH`, which outranks the host's
  `LD_LIBRARY_PATH`, so a host injection cannot shadow them either.

The **only** thing the container takes from the host is the **GPU driver** (`libcuda` /
`libnvidia-ml`, injected by `--nv`) — which is correct and how every GPU container works. Everything
else is self-contained.
